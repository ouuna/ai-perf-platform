# 设计说明（docs/design.md）

本文记录 AI 智能性能测试平台的关键设计决策与取舍。

## 1. 为什么用模板生成脚本，而非 LLM 自由生成？

LLM 自由生成 locustfile 有三个致命问题：

1. **不可控**：LLM 可能 import 危险模块（`os`、`subprocess`）、写死不可信 URL、生成结构随机的代码。
2. **不可测**：每次输出结构不同，无法写稳定的单元测试断言。
3. **不可审计**：面试/评审时无法解释"为什么这样更安全"。

**方案**：LLM 只负责产出**结构化 TestPlan**（JSON），代码由 Jinja2 模板确定性渲染。
LLM 的输出先过 Pydantic schema 校验（失败自动重试），再经三重防线：

- `ast.parse` 语法校验
- import 白名单（只允许 locust/random/json/time/csv）
- 危险调用拦截（`os.system`/`subprocess`/`eval`/`exec`/`open`/`pickle`）
- dry-run（极低并发、短时运行，验证脚本可执行）

这样 LLM 的"创造性"被限制在结构化数据层面，代码生成的正确性和安全性是确定的。

## 2. 为什么规则先于 AI？

确定性规则层先算出"事实"（拐点、SLA、异常模式、资源相关性），AI 层只做"解读"。

原因：性能分析的核心是**可验证的事实**。规则层产出一份带编号的"事实清单"
（F1, F2, ...），AI 只能基于这份清单做解读，且：

- AI 结论中每个数字必须能追溯到事实清单（数字一致性校验器，相对误差 < 5%）
- AI 引用的证据编号必须是事实清单里存在的编号
- 不确定时必须说"证据不足"，不得编造

这样即使 AI 出错，规则层的确定性结论仍然可靠；AI 的价值是"把事实解释成人话"，
而不是"凭空得出结论"。

## 3. 如何防止 AI 编造数字？

三层防护：

1. **输入约束**：AI 的 prompt 只包含事实清单 + 原始统计，不包含任何未经计算的结论。
2. **数字一致性校验器**：AI 输出中的每个数字，必须与事实清单中的某个数字
   "足够接近"（相对误差 < 5%），否则拒绝该输出并重试。
3. **证据引用校验**：AI 的 bottleneck hypothesis 必须引用事实清单里的编号，
   引用不存在的编号会被拒绝。

实测：AI 编造数字时（如引用不存在的"9999 RPS"），校验器会拦截并触发重试，
重试耗尽后返回明确错误，而不是把编造的数字写进报告。

## 4. 压测机瓶颈如何处理？

压测机本身可能成为瓶颈（CPU/内存打满），导致测出来的延迟/吞吐失真。

方案：`HostMonitor` 后台线程用 psutil 采样压测机进程的 CPU/内存，报告里单独一节
说明"压测机是否成为瓶颈"。如果压测机 CPU 接近饱和，报告中会明确提示"结论可能受
压测机资源限制，需换更强压测机复测"。

## 5. 指标口径（为什么这样定义）

- **RPS**：每秒成功+失败请求数（Locust `Requests/s`）。
- **P50/P95/P99**：响应时间分位数（Locust 输出）。
- **错误率**：失败请求数 / 总请求数。
- **拐点**：吞吐不再随并发增长、而延迟显著上升的位置——定义为"吞吐达到峰值的
  90% 且 P95 比前一阶段上升 20% 以上的点"。
- **时间序列对齐**：Locust 的 `--csv-full-history` 按秒采样，靶站 `/metrics` 按秒
  采样，统一按时间戳对齐到 `metric_points` 表。

## 6. 数据模型

- `tasks`：任务（需求、状态、时间戳）
- `test_plans`：结构化测试方案（JSON）
- `metric_points`：统一时间序列（用户数/吞吐/分位延迟/错误率/资源）
- `reports`：生成的报告（HTML/Markdown）

## 7. 取舍与已知局限

- **拐点检测**：当前用简化启发式（吞吐峰值 90% + 延迟上升），不是严格的数学拐点
  检测。对长时稳定测试更可靠，短时测试可能误判。
- **AI 解读**：依赖事实清单质量；规则层漏检的瓶颈，AI 也无法发现。
- **压测机自监控**：psutil 采样压测进程本身，若压测机与靶站同机，资源会互相干扰
  （文档已说明）。
- **spike 测试**：`LoadTestShape` 的尖峰模型目前简化处理，未完整实现。
