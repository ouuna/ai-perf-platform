# 评测说明与结果（docs/eval/README.md）

## 评测目的

验证平台对 6 种注入性能故障的瓶颈定位能力。每个故障有明确的"标准答案"
（注入的故障类型），评测平台能否通过规则分析 + AI 解读定位到正确的故障。

## 评测方法

1. 对每种故障：开启靶站对应故障 → 跑一次短时阶梯压测（最大 12 用户，约 20 秒）→
   规则分析 + AI 解读。
2. 分两个层次判定：
   - **层次 A「问题方向」**：是否识别出问题方向（延迟型 / 吞吐型 / 内存 / CPU）。
   - **层次 B「精确定位」**：是否精确定位到具体故障类型（慢查询 vs N+1 vs 锁竞争）。
3. 判定用"故障特定关键词"，通用信号（拐点/锯齿/延迟上涨）不算精确命中，
   避免虚高。

## 评测结果（真实运行）

| 指标 | 结果 |
|------|------|
| 问题方向识别准确率 | 66.7%（4/6） |
| 精确定位准确率 | 16.7%（1/6） |
| AI 定位准确率 | 0%（mock，未启用真实 AI） |

### 逐故障结果

| 故障 | 期望方向 | 方向识别 | 精确定位 |
|------|---------|---------|---------|
| slow_query（慢查询） | 延迟 | ✅ | ❌ |
| n_plus_1（N+1 查询） | 延迟 | ✅ | ❌ |
| lock_contention（锁竞争） | 吞吐 | ✅ | ✅ |
| pool_exhaustion（连接池耗尽） | 延迟 | ✅ | ❌ |
| memory_leak（内存泄漏） | 内存 | ❌ | ❌ |
| cpu_bound（CPU 密集） | CPU | ❌ | ❌ |

## 结论与诚实说明

1. **规则层能识别"有无性能问题"和"大致方向"**（延迟型问题识别较准），但
   **精确定位具体故障类型的能力弱**——无法区分慢查询、N+1、连接池耗尽这三种
   "都表现为延迟上升"的故障。

2. **memory_leak 和 cpu_bound 未识别的原因**：评测压测时长太短（约 20 秒），
   内存泄漏需要更长时间累积，CPU 饱和在短时低并发下不明显。这是评测设计的
   局限，不是平台缺陷的完整证明——更长的稳定性测试才能暴露这两类故障。

3. **AI 定位 0% 是预期结果**：评测用 MockLLM（无真实 API Key），mock 无法真正
   理解故障。真实 AI 的增量（解释质量、建议质量）需要在有 Key 时另行评测。

## 后续改进方向

- 增强规则层：为慢查询/N+1/连接池耗尽增加更精细的判别信号（如延迟-数据量相关性、
  请求次数异常、连接等待时间）。
- 增加稳定性测试场景（更长时长）以覆盖内存泄漏和 CPU 饱和。
- 接入真实 LLM 后补充"规则 vs 规则+AI"的对比评测。

## 局限声明

以上结果基于短时低并发压测，不代表平台在生产强度下的完整能力。评测如实记录，
未作夸大。
