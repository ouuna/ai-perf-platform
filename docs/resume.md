## 一、简历项目描述（可直接用）

### 项目：AI 智能性能测试平台（开源）

**一句话**：一个从自然语言需求自动生成 Locust 压测脚本、执行压测、定位瓶颈并产出
报告的开源性能测试平台。

**技术栈**：Python / FastAPI / Locust / Pydantic v2 / SQLite / Jinja2 / psutil / Docker

**核心亮点（3–5 条，量化）**：

1. 实现「自然语言需求 → 结构化测试方案 → Locust 脚本 → 自动压测 → 指标分析 →
   瓶颈定位 → 性能报告」的完整闭环，通过 `docker compose up` 一键启动平台与靶站。
2. 设计了「规则先于 AI」的分析架构：确定性规则层计算拐点/SLA/异常模式/资源相关性，
   AI 层只做解读，并通过**数字一致性校验器**拦截 AI 编造数字（相对误差 < 5% 自动拒绝）。
3. 内置 6 种可注入性能故障的电商靶站（慢查询/N+1/锁竞争/连接池耗尽/内存泄漏/CPU 密集），
   用于验证瓶颈定位准确性，规则层对性能问题的方向识别准确率 66.7%（详见评测，如实记录局限）。
4. 采用「模板渲染 + 静态校验」生成压测脚本（而非 LLM 自由生成），通过 import 白名单、
   危险调用拦截、dry-run 三重防线保证脚本安全可控。
5. 覆盖单元测试 + 集成测试 + GitHub Actions CI（lint/测试/覆盖率/Docker 构建），
   所有 LLM 相关测试用 MockLLM，无 API Key 也能完整跑通。

## 二、面试可能被追问的 10 个问题与参考回答

### Q1：为什么不让 LLM 直接生成 Locust 脚本？

**答**：因为不可控、不可测、不可审计。LLM 可能 import 危险模块、写死不可信 URL、
每次输出结构不同。我的方案是让 LLM 只产出结构化 TestPlan（JSON），代码由 Jinja2
模板确定性渲染，再经 `ast.parse` + import 白名单 + 危险调用拦截 + dry-run 三重校验。
这样代码生成的安全性和正确性是确定的，LLM 的创造性被限制在结构化数据层面。

### Q2：如何防止 AI 在性能分析中编造数字？

**答**：三层防护。第一，AI 的输入只包含规则层算出的"事实清单"和原始统计，不含结论；
第二，数字一致性校验器要求 AI 输出中的每个数字都能在事实清单中找到出处（相对误差
< 5%），否则拒绝并重试；第三，AI 的瓶颈假设必须引用事实清单里存在的证据编号。
实测编造数字会被拦截。

### Q3：为什么规则分析要放在 AI 之前？

**答**：性能分析的核心是可验证的事实。规则层（拐点检测、SLA 判定、异常模式、资源
相关性）是确定性的、可测试的，它产出带编号的事实清单。AI 的价值是把事实解释成人话，
而不是凭空得出结论。这样即使 AI 出错，规则层的结论仍然可靠。

### Q4：拐点（最大稳定并发）是怎么算的？

**答**：定义为"吞吐不再随并发增长、而延迟显著上升的位置"。具体是：在阶梯加压的
时间序列中，找到吞吐达到峰值 90% 且 P95 比前一阶段上升 20% 以上的点。这是一个
简化启发式，不是严格数学拐点，文档里如实说明了这个局限。

### Q5：怎么避免压测机本身成为瓶颈导致结论失真？

**答**：用 psutil 后台采样压测机进程的 CPU/内存，报告里单独一节说明。如果压测机
CPU 接近饱和，报告会明确提示"结论可能受压测机资源限制，需换更强压测机复测"。

### Q6：SLA 熔断是怎么实现的？

**答**：Runner 以子进程跑 locust（`--headless --csv --csv-full-history`），轮询时
实时读取 stats history CSV 里的错误率，超过熔断阈值（默认 30%）就 terminate 子进程
并记录熔断原因。避免"错误率已经爆了还在傻等压测跑完"。

### Q7：Locust 的 LoadTestShape 和 -t 参数是什么关系？

**答**：用了 LoadTestShape 后，locust 的 `-t`/`--run-time` 会被 shape 覆盖，测试时长
由 shape 的 `tick()` 返回 None 决定。我在 dry-run 时用简化脚本（无 shape）保证 `-t 3s`
生效，这个坑在实际调试时踩过并记录在案。

### Q8：MockLLM 的设计目的是什么？

**答**：让项目在无 API Key 时也能完整跑通 demo 和所有测试。LLM 抽象层统一接口，
Anthropic/OpenAI/Mock 三实现。Mock 是确定性的，测试可复现、不依赖网络。CI 里所有
LLM 相关测试都用 Mock。

### Q9：靶站的 6 种故障是怎么设计的？

**答**：每种故障有明确的"标准答案"，用于验证瓶颈定位准确性。比如 slow_query 是
无索引全表扫描（延迟随数据量上升），lock_contention 是全局锁竞争（吞吐封顶）。
靶站暴露 `/metrics` 和 `/admin/faults` 管理接口，通过开关切换故障，跑完整评测
看平台的定位准确率。

### Q10：这个项目的局限是什么？

**答**：① 拐点检测是简化启发式，短时测试可能误判；② AI 解读受规则层事实清单质量
限制，规则漏检的瓶颈 AI 也发现不了；③ 压测机与靶站同机时资源会互相干扰；④ spike
测试模型简化处理。这些都在文档里如实说明，没有夸大。
